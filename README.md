# 🤖 ربات OCR فارسی — Production Pipeline (مستر 2000 DPI)

پایپ‌لاین OCR تولیدی فارسی با **رندر مستر 2000 DPI**، معماری ناحیه‌محورِ حافظه‌امن،
جدول‌خوانی سلول‌به‌سلول، fallback چندموتوره (Google Vision → Tesseract) و
گذرهای تخصصی ارقام (فارسی/انگلیسی/مخلوط RTL-LTR).

## 🏗️ معماری

```
PDF ──▶ render.py      رندر مستر 2000DPI (TIFF lossless + metadata کامل: requested/
                       effective DPI، ابعاد PDF، حافظه، زمان رندر — بخش ۱ و ۲)
    ──▶ preprocess.py  پیش‌پردازش تحلیل‌محور: تحلیل روی تصویر کوچک، اعمال فقط عملیاتِ
                       لازم روی مستر (illumination/contrast/deskew/denoise با حفظ
                       نقطه‌های فارسی) + محافظ صفحهٔ تمیز (بدون فیلتر سنگین روی
                       سند دیجیتال) + optimal_ocr_scale کالیبره‌شده (بخش ۳)
    ──▶ layout.py      تحلیل چیدمان در مقیاس کوچک + نگاشت به مستر: جدول/متن/گرافیک (بخش ۹ و ۱۳)
    ──▶ tables.py      شبکهٔ جدول، برش سلول از مستر، strip_grid_lines، مدل منطقی جدول
                       (row/col/span/bbox/raw/normalized/conf/engine/digit_type/needs_review)
                       + خروجی JSON/CSV/HTML/XLSX/Markdown (بخش ۹ تا ۱۱)
    ──▶ engines.py     GoogleVisionEngine + TesseractEngine (docker ocr-tesseract:fa)
                       + ocr_any با fallback چندموتوره + بازیابی PSM + گذر ترمیم eng
                       برای جزیره‌های لاتین + بازسازی BiDi سطرها (بخش ۴ تا ۷ و ۱۴ و ۱۵)
    ──▶ pipeline.py    ارکستراتور: OCR ناحیه‌ای با رأی‌گیری چندمقیاسی، جدول سلول‌به‌سلول،
                       گذر گلیف عددی (قوانین شکل: صفر/۳-۴)، اعتبارسنجی، متریکس، دیباگ
                       (بخش ۱۰ و ۱۲ و ۲۰ و ۲۴ تا ۲۸)
    ──▶ metrics.py     زمان هر مرحله + اوج RAM + شمارنده‌ها (بخش ۲۵)
```

**قانون طلایی:** هر تغییری (مقیاس/برش/فیلتر) از تصویر مستر 2000DPI منشأ می‌گیرد؛
مختصات همهٔ چیزها به دستگاه مختصات مستر برمی‌گردد (بخش ۱۲).

## 🎯 قواعد دقت کلیدی (کالیبره‌شدهٔ تجربی)

- **مقیاس بهینهٔ OCR**: ارتفاع گلیف ~35–40px؛ سلول‌های بزرگ مستر در 0.05–0.22.
- **رأی‌گیری چندمقیاسی**: متن درست بین مقیاس‌ها تکرار می‌شود؛ اکثریتِ غیرخالی برنده.
- **گذر گلیف عددی**: صفر فارسی = دایرهٔ کوچک هم‌تراز خط پایه (قانون شکل)؛ ۳/۴ با
  شمارش ران‌های لبهٔ راست تفکیک می‌شوند؛ ارقام داخل عدد LTR می‌شینند.
- **گذر ترمیم eng**: مدل fas ارقام/لاتین را «لالالا»/صفر خراب می‌خواند؛ توکن‌های
  آشغالِ قطعی با هم‌پوشان گذر eng خالص تعویض می‌شوند — حروف فارسی سالم هرگز.
- **BiDi**: جزیره‌های پیوستهٔ LTR (عدد+واحد، HS Code، Institute Cargo Clauses (A))
  معکوس بازسازی می‌شوند؛ اتصال شناسه‌های خط‌تیره‌دار (INV-2026-004291).
- **صفر اتلاف داده**: خوانش‌های حل‌نشده `needs_review: true` می‌گیرند (بخش ۲۷).

## اجرای نسخهٔ شرکتی

### کنترل سرعت و منابع

گذرهای مستقل OCR بومی با حداکثر چهار پردازش هم‌زمان اجرا می‌شوند. ترتیب
رأی‌گیری، همهٔ مقیاس‌ها، کنترل ارقام و مستر ۲۰۰۰ DPI حفظ می‌شوند؛ مسیرهای
Google Vision و Docker همچنان ترتیبی هستند. نتایج کاملاً یکسان فقط داخل
همان سند، با سقف ۱۲۸ ورودی و ۴ مگابایت دادهٔ سریال‌شده بازاستفاده می‌شوند؛
حافظهٔ نهان بین کاربران یا اسناد مشترک نیست.

در نصب بومی ویندوز دارای `libtesseract-5.dll` و `libleptonica-6.dll`، مدل‌ها
داخل حداکثر چهار پردازش جداگانه برای همان سند بازاستفاده می‌شوند. وضعیت
تشخیص تطبیقی و محدودیت کاراکترها پیش از هر خوانش پاک می‌شود؛ پردازش‌ها و
حافظهٔ نهان در پایان سند، حتی هنگام خطا، بسته می‌شوند. این تغییر هیچ گذر
تشخیص یا DPI را کم نمی‌کند. در نبود کتابخانه یا خرابی پردازش، همان مسیر
خط فرمان استفاده می‌شود. `OCR_PERSISTENT_ENGINE=0` در تنظیمات خصوصی، این
بهینه‌سازی را غیرفعال می‌کند. `ocr_processes` تعداد پردازش‌های ساخته‌شده و
`ocr_native_calls` تعداد خوانش‌های انجام‌شده با مدلِ بازاستفاده‌شده است؛
`peak_rss_mb` مانند قبل حافظهٔ پردازش اصلی را اندازه می‌گیرد، نه مجموع فرزندان.

برای ارقام مشکوک، مدل مکمل خط عربی فقط روی گلیف‌های جداشده اجرا می‌شود؛
دو مقیاس باید با حداقل اطمینان توافق کنند. جداکنندهٔ مورب از شکل تصویر
تشخیص داده می‌شود. بازیابی شماره و تاریخِ سربرگ به مجاورت برچسب شناخته‌شده،
حداکثر شش میدان در صفحه و خوانش کاملِ دارای جداکننده محدود است؛ نام فایل،
تاریخِ احتمالی یا فرهنگ لغت وارد تشخیص نمی‌شود. سال‌های چهاررقمی نیز در
اولویت بازبینی هستند. خوانش اولیه و علامت بازبینی پس از اصلاح حفظ می‌شوند؛
توافق موتور تضمین درستی صددرصد نیست. منشأ و هش مدل در `tessdata/SOURCES.md` آمده است.

اصلاح پس‌زمینهٔ اسکن‌های بزرگ در چهار نوار با هم‌پوشانی ۱۵ پیکسل اجرا
می‌شود؛ خروجی پیکسلی آن با فیلتر کامل ۳۱×۳۱ یکسان است. حذف نویز نیز به‌جای
پیمایش مجدد کل تصویر برای هر لکه، از نگاشت برچسب‌ها در یک گذر استفاده می‌کند؛
آستانهٔ حذف و نقطه‌های حروف فارسی بدون تغییر باقی می‌مانند.

در JSON، مقدار `performance.total_seconds` زمان کل سند است؛ تعداد واقعی
اجرای موتور و استفاده از حافظهٔ نهان در `ocr_processes` و `ocr_cache_hits`
ثبت می‌شود. زمان خواندن مستر، ساخت تصویر کار، بازبینی ارقام و تصویر دیباگ
نیز در `pages[].metrics.timings_seconds` جداگانه ثبت می‌شود. برای بنچمارک،
همان PDF اسکن‌شده را قبل و بعد از انتشار با چند تکرار، بدون بار دیگر و از
مسیر HTTPS بارگذاری کنید؛ متن، ارقام، ساختار جدول و دانلود ZIP را نیز مقایسه کنید.

رابط وب از فونت محلی وزیر بولد، متن‌های رسمی و کنترل‌های متنی استفاده می‌کند.
موتور Tesseract بومی نیز پشتیبانی می‌شود؛ مسیر اجرایی آن با `TESSERACT_CMD`
و پوشهٔ مدل‌ها با `OCR_TESSDATA_DIR` قابل تنظیم است. مسیر Docker همچنان پشتیبانی می‌شود.

نسخهٔ عمومی با Waitress پشت IIS اجرا می‌شود. کلید نشست، کلید Google Vision و
داده‌های کاربران در پوشهٔ خصوصی خارج از مخزن و ریشهٔ وب نگهداری می‌شوند.
بارگذاری‌ها به PDF معتبر، حداکثر ۱۰۰ فایل و ۳۰۰ صفحه در هر نوبت محدود هستند.
دریافت نتیجه به نشست همان مرورگر وابسته است. صف هم‌زمان محدود است و در صورت
کمبود فضای دیسک، درخواست جدید پذیرفته نمی‌شود؛ اسناد موجود حذف نمی‌شوند.

ترتیب انتشار الزامی:

```powershell
python -m unittest discover -s tests -v
git add <changed-source-files>
git commit -m "Describe the change"
git push origin main
.\deploy.ps1
```

اسکریپت انتشار فقط نسخهٔ تمیز و پوش‌شده به `origin/main` را منتشر می‌کند و
نسخه‌های قبلی را حفظ می‌کند. گزینهٔ `-ProvisionDomain` برای آماده‌سازی اولیهٔ
DNS و گواهی HTTPS زیر دامنهٔ `ocr.gomrok.org` است. هیچ کلید، فایل بارگذاری‌شده
یا خروجی پردازش نباید به Git اضافه شود.

اعداد فارسی دارای گلیف‌های مشابه، از برش‌های مستقل تصویر مستر نیز بررسی
می‌شوند. در صورت اختلاف، خوانش اولیه در `raw_ocr_text` نگهداری و نیاز به
بازبینی در خروجی JSON و رابط کاربری اعلام می‌شود؛ خوانش ناقص یا نامطمئن
جایگزین مقدار اصلی نمی‌شود.

### یکدستی ارقام و بازخوانی نواحی مشکوک

تمام ارقام متن، سطرها، واژه‌ها و جدول‌های خروجی فارسی هستند؛ مقدار عدد،
صفرهای ابتدایی، جداکنندهٔ هزارگان، ممیز و اجزای شناسه حفظ می‌شوند.
`raw_text` و `raw_ocr_text` خوانش اولیه را نگه می‌دارند و
`normalized_en_digits` نسخهٔ دارای ارقام انگلیسی برای مصرف ماشینی است.
در جدول‌ها نیز هر دو نسخهٔ ارقام و خوانش اولیه موجود است.

بازخوانی رقم منفرد با ارتفاع واقعی جوهر مقیاس می‌شود. گذرهای مستقل باید
توافق کنند؛ گذر سوم فقط برای رقم‌های اختلافی اجرا می‌شود. جداکنندهٔ قابل
تشخیص از تصویر به صفر تبدیل نمی‌شود و خوانش حل‌نشده برای بازبینی علامت می‌خورد.
انتخاب چندمقیاسی، اطمینان صفر را محاسبه می‌کند و در رأی مساوی از اطمینان
بالاتر استفاده می‌کند. گذر انگلیسی فقط با شواهد کافی جایگزین ناحیه می‌شود.

واژه‌های کم‌اطمینان دارای `*` از برش تصویر دوباره خوانده می‌شوند؛ جایگزینی
به توافق دو مقیاس و حفظ سایر کاراکترها وابسته است. ستاره‌های واقعی یا
خوانش‌های حل‌نشده حذف نمی‌شوند و `needs_review` دارند. سقف بازخوانی
۱۶ واژهٔ مشکوک در هر صفحه است. فرمول‌های احتمالی استخراج‌شده در خروجی‌های
صفحه‌گسترده به‌صورت متن ذخیره می‌شوند.

### دقت اسکن‌های نامه و جدول

شبکهٔ هر جدول از خطوط متصل همان جدول تشخیص داده می‌شود؛ حاشیهٔ اسکن و
خط سربرگ به جدول سراسری تبدیل نمی‌شوند. حذف حاشیه فقط روی ماسک تحلیل
انجام می‌شود و PDF اصلی و تصویر مستر بدون تغییر باقی می‌مانند.

شناسهٔ سطر موتور در بازسازی متن حفظ می‌شود تا واژه‌های سطرهای نزدیک یا
کج با هم مخلوط نشوند. داخل سلول‌ها، خطوط کم‌رنگِ حاشیه پیش از تشخیص
اندازهٔ حروف حذف می‌شوند و سطرهای دارای فاصلهٔ واضح جداگانه خوانده می‌شوند.
برای سلول تک‌سطری کم‌اطمینان، دو بازخوانی مستقل با حالت خط خام انجام
می‌شود؛ جایگزینی فقط با توافق، حداقل اطمینان و بهبود نسبت به خوانش اولیه
پذیرفته می‌شود. خوانش اولیه و علامت بازبینی حفظ می‌شوند.

نام خروجی جدول شامل شمارهٔ صفحه است تا جدول‌های صفحات مختلف روی هم
نوشته نشوند. اطمینان موتور، درصد دقت واقعی نیست؛ مخصوصاً نام‌ها، تاریخ‌ها
و ارقام اسکن کم‌کیفیت باید با تصویر اصلی ارزیابی شوند. افزایش DPI به‌تنهایی
جزئیات ازدست‌رفتهٔ اسکن را بازیابی نمی‌کند. نمونه‌های مشتری وارد مخزن یا
آزمون عمومی انتشار نمی‌شوند.

در پاراگراف‌های متراکم، حالت متن پراکنده فقط با حفظ پوشش حروف و افزایش
معنادار اطمینان جایگزین می‌شود؛ بالا رفتن میانگین اطمینان بر اثر حذف سطر
دشوار، به‌تنهایی دلیل انتخاب نیست. حالت بلوکِ کامل‌تر با اطمینان نزدیک
نیز بررسی می‌شود. این کنترل از همان گذرهای موجود استفاده می‌کند.

### استخراج محلی دقیق و بازبینی اختیاری

حالت `OCR_ACCURACY_MODE=maximum_local` خوانش مستقل PaddleOCR را کنار
Tesseract فعال می‌کند. پردازش فقط از تصویر اصلی PDF و نسخه‌های غیرمولد آن
استفاده می‌کند؛ واژه یا عدد از نام فایل، تاریخ احتمالی یا فرهنگ لغت حدس زده
نمی‌شود. حالت سازگار `legacy` برای مقایسه و بازگشت نگهداری شده است.
`OCR_LOCAL_ONLY` به‌صورت پیش‌فرض `1` است و در حالت دقیق، Google Vision حتی
با وجود کلید قدیمی استفاده نمی‌شود.

مدل‌های `PP-OCRv5_server_det` و `arabic_PP-OCRv5_mobile_rec` در محیط جداگانهٔ
CPU با Python 3.11 اجرا می‌شوند. فایل‌های مدل به commit ثابت و SHA-256
مقیدند؛ منبع زبان فارسی در
[مستندات رسمی PaddleOCR](https://www.paddleocr.ai/latest/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html)
آمده است. پشتیبانی از زبان به معنی عبور از معیار دقت این پروژه نیست.
وابستگی‌های ویندوز در `requirements-paddle.lock` ثابت شده‌اند و نباید
در محیط Flask نصب شوند.

آماده‌سازی مدل و محیط، پیش از انتشار و خارج از Git و ریشهٔ IIS انجام می‌شود:

```powershell
# مسیرهای نسخه‌دار نمونه‌اند؛ محیط موجود را بازنویسی نکنید.
python -m venv C:\Websites\ocr.gomrok.org\local-ocr\runtime-v5-20261019
python tools\provision_local_ocr.py --lock requirements-paddle.lock --wheelhouse <verified-wheelhouse> --python C:\Websites\ocr.gomrok.org\local-ocr\runtime-v5-20261019\Scripts\python.exe
python tools\provision_local_ocr.py --models C:\Websites\ocr.gomrok.org\local-ocr\models-v5-20261019
```

نصب، اندازهٔ بازشدهٔ بسته‌ها را با ذخیرهٔ ایمنی ۱۵۳۶ مگابایت بررسی می‌کند؛
در کمبود فضا متوقف می‌شود و چیزی از اسناد یا نسخه‌های قبلی حذف نمی‌کند.
مسیرهای نهایی با `OCR_PADDLE_PYTHON` و `OCR_PADDLE_MODELS` در تنظیمات خصوصی
ثبت می‌شوند. worker مدل دانلود نمی‌کند، ورودی شبکه‌ای نمی‌پذیرد و اتصال
socket آن غیرفعال است؛ این کنترل جای فایروال سیستم‌عامل نیست. متغیرهای
حاوی کلید نشست یا کلید سرویس‌های ابری به worker منتقل نمی‌شوند.
سقف تصویر ۲۰ مگاپیکسل و ۲۴ مگابایت، حافظهٔ درخت worker برابر ۸ گیگابایت،
هر درخواست تشخیص ۶۰۰ ثانیه و خوانش ۱۲۰ ثانیه است. سقف حافظه بر اساس
مصرف اندازه‌گیری‌شدهٔ مسیر CPU تنظیم شده و در ویندوز با Job Object و
بررسی مجموع حافظهٔ فرزندان اعمال می‌شود؛ بسته‌شدن هماهنگ‌کننده،
فرزندان همان worker را نیز می‌بندد. در سایر سیستم‌ها نظارت حافظه
نمونه‌برداری‌شده است و باید محدودیت سیستم‌عامل جداگانه تعریف شود.
تشخیص سرور در محیط ویندوزِ آزموده‌شده، به‌دلیل ناسازگاری oneDNN با یک
ویژگی مدل، از مسیر FP32 بدون oneDNN استفاده می‌کند.

گذر جزئیات از قطعات ۱۰۲۴ پیکسلی با هم‌پوشانی ۱۲۸ پیکسل استفاده می‌کند؛
کنترل نواحی فاقد خوانش نیز قطعه‌ای است و ریزمتن را برای تحلیل پوشش کوچک
نمی‌کند. نمای کلی فقط برای اتصال سطرهای عبوری از مرز قطعات استفاده می‌شود.
چرخش برش سطر با گسترش بوم انجام می‌شود تا حروف حاشیه قطع نشوند. برای اسکنِ
تمام‌صفحه، دست‌کم ۱٫۵ برابر نمونه‌برداری پیکسل اصلی و حداقل ۳۰۰ DPI
(تا سقف انتخاب کاربر و ۶۰۰ DPI) حفظ می‌شود؛ صفحات برداری تا ۶۰۰ DPI بررسی
می‌شوند. این گذر جای مسترِ وضوح انتخابی کاربر را نمی‌گیرد و مقدار واقعی
در `precision_render_dpi` ثبت می‌شود. بزرگ‌سازی، جزئیات ازدست‌رفته نمی‌سازد.
سقف هر صفحه ۱۲۸ قطعه، ۲۰۴۸ سطر و ۲۵۶ بررسی عددی است. بودجهٔ ۴۰ دقیقه‌ای
گذر جزئیات بین فراخوانی‌ها بررسی می‌شود و شامل گذر اولیهٔ OCR نیست؛
هر فراخوانی سقف زمانی مستقل دارد. نواحی یا سلول‌های بررسی‌نشده و اثر
نوشتهٔ فاقد خوانش به‌صراحت گزارش می‌شوند.

`pages[].review_units` متن نهایی و مختصات آن روی PDF اصلی را نگه می‌دارد.
`words` و `raw_text` خوانش اولیه‌اند و با اصلاح خودکار یا دستی بازنویسی
نمی‌شوند؛ منشأ آن‌ها با `words_source` و `final_text_source` مشخص است.
`engines`، `coverage`، `precision_warnings`، `numeric_checks` و `candidates`
اطلاعات افزوده‌اند و قراردادهای بارگذاری، وضعیت و دانلود قبلی باقی می‌مانند.
توافق مستقل فقط یک شاهد است، نه درصد دقت یا تضمین صحت. وجود خوانش متناقض
حتی کنار یک توافق بین دو موتور، ابهام را حفظ می‌کند؛ رأی تکراری همان موتور
آن را رفع نمی‌کند. سطرهای خارج از بودجه با خوانش موقت و موقعیتشان باقی
می‌مانند. `ambiguities` تعداد سطرها، سلول‌ها و بررسی‌های عددی نامطمئن را گزارش
می‌کند و `document.second_engine` شکست یا آماده‌نشدن موتور دوم را مشخص می‌کند.

پس از استخراج، بازبینی تصویر و سطر/سلول اختیاری است. مسیرهای
`/review/<job>/<document>` و `/preview/<job>/<document>/<page>` فقط برای
نشست مالک قابل دسترسی‌اند. ذخیرهٔ اصلاحات به CSRF و شمارهٔ نسخهٔ جاری نیاز
دارد؛ نسخهٔ قدیمی پاسخ 409 می‌گیرد. قفل فایل از ذخیرهٔ هم‌زمان میان
فرایندهای سرویس نیز جلوگیری می‌کند. هر ذخیره مجموعهٔ هماهنگ TXT، JSON،
CSV، HTML، XLSX و ZIP می‌سازد و تنها پس از تکمیل، اشاره‌گر نسخه را منتشر
می‌کند. خطای ساخت Excel دیگر بی‌صدا نادیده گرفته نمی‌شود.
پیش‌نمایش با فرایند مستقل، سقف ۵۱۲ مگابایت و ۲۰ ثانیه و حداکثر دو
درخواست هم‌زمان ساخته می‌شود؛ شکست آن خروجی‌های قبلی را تغییر نمی‌دهد.
شکست ذخیره فقط فایل‌های منتشرنشدهٔ همان تلاش را پاک می‌کند؛ اندازهٔ واقعی
خروجی و ذخیرهٔ ایمنی پیش از انتشار اشاره‌گر دوباره بررسی می‌شوند.
اصل PDF، خروجی خودکار و نسخه‌های قبلی حفظ می‌شوند. سقف هر درخواست ۱
مگابایت و ۲۰۰۰ اصلاح، هر متن ۸۱۹۲ نویسه، و هر سند ۱۰۰ نسخه و ۶۴ مگابایت
فضای بازبینی است. پس از راه‌اندازی مجدد، نشست دارای کلید پایدار به
بازبینی‌های کامل قبلی دسترسی دارد؛ پردازش نیمه‌تمام به‌اشتباه موفق اعلام
نمی‌شود.

اندازهٔ دادهٔ پایهٔ بازبینی و هر بار خواندن آن نیز حداکثر ۱۶ مگابایت است؛
عبور از این حد، خروجی خودکار موجود را مسدود یا بازنویسی نمی‌کند.

### معیار انتشار نسخهٔ دقیق

مرجع دستی و PDFهای نمونه فقط در فضای خصوصی آزمون نگهداری می‌شوند.
`tools/evaluate_accuracy.py` خروجی خودکار پنج صفحه را با مرجع دارای هش
منبع می‌سنجد: CER حداکثر ۰٫۵٪، WER حداکثر ۲٪، پوشش سطر حداقل ۹۹٪ و
تطبیق تمام شناسه‌ها، تاریخ‌ها و سلول‌های جدول. فاصلهٔ بین کلمه‌ها حذف
نمی‌شود؛ تفاوت شکل ارقام و حروف فارسی/عربی و نیم‌فاصلهٔ نمایشی هم‌سطح
می‌شود. پوشش سطر با تطبیق یکتای سطرهای مرجع و حداکثر ۲۰٪ فاصلهٔ نویسه‌ای
سنجیده می‌شود و به‌تنهایی جای معیار CER/WER را نمی‌گیرد.

گزارش باید از اجرای کامل همان کد و مدل‌ها، پیش از اصلاح دستی، باشد.
اجرای گذر جزئیات روی نتیجهٔ قدیمی صرفاً آزمون تشخیصی است و برای انتشار
پذیرفته نمی‌شود. پنج صفحه باید یکتا باشند؛ سطر یا سلول تکراری، صفر ابتدایی
جاافتاده، ساختار اشتباه جدول و توقف موتور باعث رد معیار مربوط می‌شوند.
هش کد، مدل‌های هر دو موتور و ابزار ارزیابی در شواهد لحاظ می‌شود؛ تفاوت
پایان خط Git در ویندوز هش معنایی کد را تغییر نمی‌دهد. اسکریپت انتشار
علاوه بر تمیزی Git و تطبیق `origin/main`، این گزارش و فضای انتشار را
بررسی می‌کند:

```powershell
python tools\run_acceptance.py --reference <private-reference.json> --source freight=<absolute-source.pdf> --source circular=<absolute-source.pdf> --output <new-private-evidence-directory>
python tools\evaluate_accuracy.py --reference <private-reference.json> --results <automatic-results.json> --output <private-report.json>
python -m unittest discover -s tests -v
# فقط پس از عبور از معیارها: commit و push
.\deploy.ps1 -AccuracyReport <private-report.json> -PaddlePython <private-versioned-python.exe> -PaddleModels <private-versioned-models>
```

در صورت شکست معیارها انتشار انجام نمی‌شود. پس از انتشار مجاز، سلامت HTTPS
و بارگذاری/دریافت واقعی با PDF تولیدشدهٔ آزمون روی دامنه بررسی می‌شود؛
اسناد مشتری برای آزمون عمومی ارسال نمی‌شوند. پردازش فعال نباید متوقف شود.
برای جلوگیری از ورود درخواست میان بررسی سلامت و تعویض نسخه، انتشار
پذیرش بارگذاری جدید را می‌بندد و درخواست‌های در حال پذیرش را هم می‌شمارد؛
بارگذاری در این فاصله پاسخ 503 می‌گیرد، اما وضعیت و دریافت در دسترس‌اند.
نسخهٔ قبلی که این وضعیت را تأیید نمی‌کند، خودکار متوقف نمی‌شود و به
تحویل کنترل‌شده در زمان نگهداری نیاز دارد. علامت نگهداری ساخته‌شده توسط
اسکریپت در پایان موفق یا ناموفق برداشته می‌شود.

آزمون‌های واحد ظرفیت دیسک را مستقل از وضعیت میزبان شبیه‌سازی می‌کنند و
مسیرهای کمبود فضا را جداگانه می‌سنجند. این شبیه‌سازی جای آزمون پذیرش واقعی
یا بررسی فضای نصب و انتشار را نمی‌گیرد. اجرای کامل پنج صفحه با رندر ۲۰۰۰
DPI به‌صورت محافظه‌کارانه حدود ۳٫۴۳ گیگابایت فضای آزاد با احتساب ذخیرهٔ
ایمنی درخواست می‌کند؛ هیچ سند یا نسخهٔ قبلی برای فراهم‌کردن آن حذف نمی‌شود.
